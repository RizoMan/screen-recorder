# RUSTDOC PRODUCTION-GRADE DOCUMENTATION STANDARDS
ID: `RULE-DOC-001`
Status: MANDATORY / ZERO WARNING TOLERANCE

---

## 1. Zero Doc Warning Policy
- The entire workspace must compile cleanly with `cargo doc --workspace --no-deps`.
- Any compiler warning generated by rustdoc (`broken_intra_doc_links`, `missing_docs` where enforced, invalid markdown) is considered a blocking build error.

---

## 2. Mandatory Structural Sections
Every public struct, enum, trait, method, and function must include Rustdoc documentation (`///` or `//!`) containing standard GitHub Flavored Markdown sections where applicable:

### Function / Method Structure
```rust
/// Short one-line summary of what this function or method does.
///
/// Longer paragraph providing architectural context, operational invariants,
/// and relationship to `[REQ-...]` or `[CONTRACT-...]`.
///
/// # Arguments
///
/// * `param1` - Explanation of the parameter and expected range.
/// * `param2` - Explanation of the parameter.
///
/// # Returns
///
/// Describes the returned value or data structure.
///
/// # Errors
///
/// Exhaustively enumerates every condition under which this function returns `Err(...)`.
///
/// # Safety
///
/// (Mandatory if the function is `unsafe`): Details exact caller obligations.
///
/// # Examples
///
/// ```rust
/// use rec_core::pixel_format::PixelFormat;
///
/// let fmt = PixelFormat::Rgba;
/// assert_eq!(fmt.bytes_per_pixel(), 4);
/// ```
```

### Module and Trait Structure
- Every file must begin with an inner doc comment `//!` providing module overview, role within the Clean Architecture topology, and relevant `[SPEC-...]` tags.
- Traits must document their contract invariants, thread-safety assumptions (`Send + Sync`), and expected lifecycle.
